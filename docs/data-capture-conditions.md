# Условия сбора данных: сценарии, консистентность, время, команда (v1)

**Фиксация Маши, 03.07.2026.** Две самые сложные задачи продукта — консистентность
данных и время. Третья недопроработанная — принадлежность съёмок пользователям
(работа команды). Этот документ фиксирует условия, при которых мы вытаскиваем
максимум данных, и правила, которые делают их непротиворечивыми.

Дополняет `pipeline-event-journal-spec.md` (журнал — куда всё складываем).

## 1. Лестница сценариев: что можем вытащить при каких условиях

### A · Максимум: live tethered-съёмка
**Условия:** desktop-приложение запущено; фотограф указал путь к сессии C1
на своём компе; у приложения есть право чтения папки; C1 пишет сессию.
**Вытаскиваем:** появление каждого кадра в реальном времени (`frame_captured`
с НАШИМ UTC-таймштампом — камера и таймзона не участвуют), рейтинги и ключевые
слова из .cos, реестр кадров и `Exp_Date` из .cosessiondb, имя камеры,
хэши RAW-файлов. Журнал фото начинается с рождения кадра. Пульс — live.

### B · Постфактум: путь к сессии указан после съёмки
**Условия:** тот же комп (или копия папки сессии целиком); сессия не «почищена».
**Вытаскиваем:** полный реестр кадров, `Exp_Date` (интервалы между кадрами —
верны даже при сбитых часах камеры), рейтинги, ключевые слова, `ZIMPORTDATE`.
**Ограничение:** абсолютное время восстанавливаем через якорь (см. §3),
live-событий нет. Пульс восстановим полностью.

### C · Только превью (drag&drop / веб-загрузка)
**Условия:** нет доступа к сессии; загружены jpg-превью.
**Вытаскиваем:** имена файлов, EXIF из JPG (если сохранился при экспорте).
**Ограничение:** история фото начинается с `preview_loaded`; интервалы съёмки —
только если EXIF-время уцелело; иначе пульса нет, только пайплайн-события.

### D · Участник по share-ссылке (клиент, ретушёр без установки)
**Условия:** валидный share-токен; действия в веб-клиенте.
**Вытаскиваем:** только события платформы — открытия, отбор, комментарии,
аппрувы/возвраты — с актором и нашим UTC-временем. Данных сессии нет.

### E · Команда: несколько устройств и фотографов
**Условия:** участник авторизован И проект ему расшарен (роль).
Каждый указывает путь к СВОЕЙ сессии на СВОЁМ компе — события вливаются
в общий журнал проекта со своим actor и device_seq.
**Правило принадлежности:** «мои съёмки» = проекты, где я владелец или участник;
внутри проекта «моё» = события, где actor — я. Съёмка (сессия C1) всегда
привязана к проекту, а не к пользователю напрямую; пользователь видит массив
своих съёмок через членство в проектах.

## 2. Консистентность: правила

1. **Единый журнал, append-only** (см. спеку журнала). Никаких параллельных
   источников правды.
2. **Идентичность фото = хэш RAW.** В .cosessiondb уже есть
   `ZRAWFILEQUICKHASH` / `ZRAWFILEFULLHASH` — используем как основу `photo_id`:
   переживает переименование, копирование между компами, повторный импорт.
   Для сценария C (только превью, хэша RAW нет) — фолбэк: хэш превью + имя,
   с последующей склейкой при появлении сессии (событие `identity_merged`).
3. **Идемпотентный импорт.** Повторное чтение той же сессии не плодит дубли:
   ключ дедупликации — (photo_id, type, source, ts_округлённый).
4. **Merge между устройствами:** порядок (ts, device_seq); append-only снимает
   конфликты правок. Спорные состояния (два отбора) решает событие с поздним ts,
   история обоих видна в дереве.

## 3. Время: правила

1. **Храним только ISO 8601 UTC** с явным Z. Локальное время — исключительно
   при отображении. Проверка — `scripts/audit_utc.py`.
2. **Часы камеры не доверяем никогда.** EXIF/Exp_Date используем для
   ИНТЕРВАЛОВ (они верны при любом сдвиге часов), не для абсолютного времени.
3. **Якорь абсолютного времени** (по убыванию точности):
   live-событие watcher'а (сценарий A) → `ZIMPORTDATE` сессии (B) →
   время загрузки превью к нам (C). Абсолютное время кадра =
   якорь + (Exp_Date кадра − Exp_Date первого кадра).
4. Событие фиксирует и якорь, и исходник (`meta.exp_date_raw`) — пересчёт
   возможен задним числом, если якорь уточнится.

## 4. Открытые вопросы (проверить на ближайшей съёмке)

1. `Exp_Date` при tethered: ставит ли C1 его по часам компьютера или из EXIF
   камеры? Тест: один кадр, сравнить EXIF ↔ Exp_Date ↔ mtime.
2. Ведёт ли C1 `ZIMPORTDATE` для tethered-кадров (в тестовой сессии поле пустое).
3. Хэши RAW: заполняются ли ZRAWFILEQUICKHASH сразу или лениво (в тестовой
   сессии проверить не удалось — RAW удалены).
