# Журнал событий фото — спецификация (v1)

**Решение Маши, 03.07.2026.** Единый журнал событий по фото — единственный источник правды.
Всё, что видно про съёмку / контейнеры / фотографии, — производные от журнала.
Заменяет три параллельных источника (proj._events, _stageHistory, облачные stage_events).

## 1. Принципы

1. **Append-only.** События не редактируются и не удаляются — только добавляются.
   Исправление = новое событие.
2. **Per-photo.** Каждое событие ссылается на группу фото. Групповое действие —
   одно событие со списком, не N событий.
3. **Стабильная идентичность фото.** События ссылаются на `photo_id`, не на имя файла.
   Переименование — тоже событие (`renamed`), история не рвётся. Это чинит главную
   дыру текущей модели (артикулы → rename → фото теряло историю).
4. **Этап — производная.** Ни у фото, ни у проекта нет поля «этап». Этап фото =
   маппинг последнего этапо-движущего события. Счётчики этапов = свёртка журнала.
5. **Ветвление — это норма.** Процесс, который все считают линейным, ветвится:
   часть фото ушла на ретушь, часть вернулась, часть переименовывалась параллельно.
   Дерево событий должно показывать это явно, по группам фото.

## 2. Схема события

```js
{
  id:        'ev_...',            // uuid
  ts:        '2026-07-03T14:02:11Z',
  seq:       184,                 // монотонный счётчик устройства (для стабильного merge)
  type:      'selection_approved',// см. реестр типов, раздел 3
  actor:     { role: 'client'|'photographer'|'retoucher'|'system', name: 'Лена' },
  photos:    ['ph_a1', 'ph_b2'],  // photo_id; пустой массив = событие всего проекта
  group:     'Карточка 03',       // опциональная человекочитаемая метка группы
  from:      'selection',         // опционально: явный переход этапов
  to:        'client',
  meta:      { ... }              // тип-специфично: rating, old_name/new_name, версия ЦК...
}
```

`photo_id` — генерируется при первом появлении фото (импорт превью или событие
сессии), хранится в объекте фото. Маппинг имя→id поддерживается деривацией
из событий `renamed`.

## 3. Реестр типов событий (по источникам)

### Сессия Capture One (session watcher / Rate Setter)
- `session_started` / `session_ended` — разметка смены
- `frame_captured` — новый кадр (из таймштампов сессии; основа «Пульса съёмки»)
- `rating_set` — рейтинг (meta.rating)
- `keywords_written` — запись ключевых слов в COS

### Превью и отбор
- `preview_loaded` — фото появились в проекте
- `preselect_passed` — прошли преотбор
- `selection_formed` — отбор команды сформирован (группа)
- `added_to_card` / `removed_from_card` — слоты карточек (meta.card, meta.slot)
- `container_added` / `container_removed` — контейнеры «Другого»

### Клиент (share)
- `share_opened` — клиент открыл ссылку (actor.role=client)
- `selection_added` / `selection_removed` — клиент изменил отбор
- `selection_approved` — согласовано (группа фото)
- `selection_returned` — возвращено на доработку (meta.comment)
- `comment_added` — комментарий (meta.text, meta.target: card|photo)
- `annotation_added` — аннотация на фото

### Версии и постпродакшн
- `cc_loaded` — загружена ЦК-версия (meta.version)
- `cc_confirmed` — ЦК финальная
- `retouch_task_formed` — ТЗ на ретушь собрано
- `retouch_loaded` — загружена ретушь-версия
- `retouch_approved` / `retouch_returned`
- `adaptation_done`, `delivered`

### Данные
- `renamed` — meta.old_name → meta.new_name (артикулы, ручной rename)
- `article_linked` — фото/карточка связаны с артикулом (meta.article)
- `manual_stage` — ручной перевод группы (эскейп-хетч, явные from/to)

Маппинг тип→этап — один словарь `EVENT_TYPE_TO_TASK` (уже существует в events.js,
дополняется). Типы без маппинга этап не двигают (комментарии, rename).

## 4. Деривации (что рисуем из журнала)

1. **Счётчики этапов.** Свёртка: для каждого фото — последнее этапо-движущее
   событие → корзина. Этап без фото НЕ показывается (уже так в компакт-режиме).
   Требование Маши: это видит каждый участник процесса.
2. **Дерево развития событий.** Узлы — события, сгруппированные по (type + группа
   фото + окно времени); ветка возникает, когда подмножество фото уходит по
   другому пути (согласовали 40, вернули 12 → развилка). Рёбра — следование
   групп. Подпись узла: событие, счётчик фото, актор, время. Клик — список фото.
3. **Пульс съёмки.** Кардиограмма из `frame_captured` (уже на лендинге — сюда
   же источник для продукта).
4. **История кадра** (модалка E9 из UI-спеки) — фильтр журнала по одному photo_id.
5. **Метрики** (SLA, итерации, first-pass rate) — свёртки журнала, не отдельный учёт.

## 5. Синхронизация

- Локально: журнал в проекте (append), как сейчас _events.
- Облако: таблица `photo_events` (append-only, RLS по проекту), пишется тем же
  RPC-паттерном, что stage_events. Merge: (ts, device_seq) — конфликтов нет,
  т.к. append-only; порядок стабилен.
- Существующие stage_events и _stageHistory мигрируются разово в журнал
  (грубые события `manual_stage` с историческими датами).

## 5b. Связанные документы

Условия сбора данных по сценариям (A-E), правила консистентности (photo_id из
хэша RAW), времени (якорь + интервалы, ISO UTC) и принадлежности съёмок команде —
см. `data-capture-conditions.md`.

## 6. Фазы внедрения

1. **Ф1 — ядро.** photo_id + schema + маппинг; эмиттеры для уже работающих мест
   (превью, отбор, карточки, rename с событием `renamed`). Миграция легаси.
2. **Ф2 — клиентский канал.** share-действия пишут события per-photo
   (approved/returned/added/removed/comment) вместо только stage_events.
3. **Ф3 — деривации + рендер.** Счётчики этапов из журнала (скрытие пустых),
   новый рендер пайплайна в потоке DOM (вариант Б из разбора отрисовки),
   дерево событий по группам.
4. **Ф4 — сессия.** События съёмки из session watcher (frame_captured, rating_set)
   → «Пульс» в продукте.
5. **Ф5 — облако.** Таблица photo_events + merge + миграция stage_events.

Порядок Ф3/Ф4 можно поменять по приоритетам Маши.
